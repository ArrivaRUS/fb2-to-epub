# Архитектура нативного UI — fb2-to-epub (Architect #1 / Claude)

> Замена AppleScript-апплета нативным окном «Установка + Статус» + экран «Выбор обложки».
> Движок (watcher + Calibre + launchd + installer.sh) сохраняется; расширяется только под обложки.
> Дата: 2026-06-25. База: PRD/plans.md, decisions/log.md, утверждённые макеты `design/mockups/*.html`.

---

## Итог (3–5 строк)
Рекомендую **нативный SwiftUI** (не webview): на машине уже стоит полный Xcode 14 + swift 6.3, сборка идёт через `swiftc`/`swift build` (SPM) **без** `.xcodeproj`, бандл собирается тем же скриптом и переиспользует существующий ad-hoc-codesign-с-ретраем и dmgbuild. UI — тонкий слой над **неизменным** движком: статус читается из `launchctl print` + нового **структурированного state-файла JSON**, который watcher пишет атомарно; управление папкой/агентом — вызовом существующего `installer.sh`. Очередь обложек — это **файловая очередь в App Support** (по одному JSON-файлу на книгу + скачанные превью); cover-finder расширяется до режима «отдать top-N кандидатов вместо первого», а применение выбора — отдельный шаг через `ebook-polish`/`ebook-meta`. IPC «агент ↔ приложение» — только файлы + `DispatchSource`-watch каталогов (никакого сетевого канала, никакого демона у приложения).

## 1. Рекомендация по стеку: нативный SwiftUI (с честными минусами)

### Вердикт
**SwiftUI-приложение, собираемое через Swift Package Manager (`swift build`) + ручная сборка `.app`-бандла скриптом.** Полный Xcode не нужен для самой сборки (нужен один раз поставленный toolchain — он есть), `.xcodeproj` не заводим.

### Почему нативно, а не webview-обёртка
Сравнил три варианта против реальных ограничений проекта:

| Критерий | Нативный SwiftUI | WKWebView + наш HTML | Гибрид |
|---|---|---|---|
| Ощущение нативности | максимум (вибранси, system controls, фокус, шрифты) | «почти», но в окне всегда живёт веб-рантайм; скролл/контекст-меню/перетаскивание ощущаются чужими | средне |
| Объём работы (UI с нуля) | выше: верстаем 3 экрана на SwiftUI по дизайн-спеке | ниже: HTML почти готов | переменный |
| Объём работы (стыковка с движком) | **ниже**: вызовы launchctl/installer/файлов — нативно, без моста | **выше**: нужен JS↔Swift мост (`WKScriptMessageHandler` + `evaluateJavaScript`) для КАЖДОГО действия (статус, смена папки, очередь, выбор обложки) — это и есть основная работа, и она дублирует логику | двойная |
| Размер бандла | маленький (~неск. МБ, без рантаймов) | маленький (WKWebView системный) | маленький |
| macOS 11+ | да (SwiftUI 2 покрывает нужное; пара API за `if #available`) | да | да |
| Сборка без Xcode-проекта | да (`swift build`) | да | да |
| Codesign/iCloud-гонка | **тот же** механизм, что сейчас | тот же | тот же |
| Риск «webview выглядит как сайт в окне» | нет | да (премиум-тёмный дизайн усилит ощущение «это страница») | частично |

**Ключевой довод против webview:** кажущаяся экономия («HTML готов») обманчива. Готова **картинка**, но не поведение. Каждое действие всё равно надо проводить в движок через JS-мост, а это ровно та логика, которую в нативе пишешь напрямую и проще. Webview экономит вёрстку, но добавляет мост и отнимает нативность — для утилиты, которую человек видит как «системную», это плохой размен. Дизайн-спека (гейт G3) всё равно даёт точные размеры/цвета — перенести их в SwiftUI-вью не дороже, чем отлаживать мост.

**Второй довод:** дизайн тёмный, «премиум», с системными иконками-галочками и пилюлями статуса — на нативных контролах это читается как приложение; в webview — как встроенный сайт. А именно «нативность» названа в брифе главным критерием.

### Минусы нативного пути (честно)
- **Вёрстку 3 экранов делаем заново** на SwiftUI — HTML-макет переиспользуется только как эталон значений (через дизайн-спеку), не как код.
- **SwiftUI на macOS 11** имеет шероховатости (часть модификаторов и `.task`/`Material` — с 12). Лечится: минимальный таргет 11, отдельные ветки через `if #available(macOS 12, *)`; если 11 окажется дорогим — поднять флор до 12 (решение человека, см. Риски).
- **Точный пиксель-перфект тёмной темы** (градиентные рамки, корешок-блик у обложек, mask-composite-кольцо выбранного) на SwiftUI требует аккуратной работы со слоями (`.overlay`, `AngularGradient`, `mask`). Это решаемо, но это работа Developer-а + жёсткий design-review.
- Нужен **Swift-разработчик-навык** в команде (агент `developer`) — больше, чем для HTML.

### Если человек выберет webview (запасной вариант)
Тонкое `NSWindow` + `WKWebView`, грузящий локальный `index.html` из бандла. Мост: `window.webkit.messageHandlers.bridge.postMessage({action,…})` → Swift выполняет (launchctl/installer/файлы) → ответ через `webView.evaluateJavaScript("window.onEngineEvent(…)")`. Очередь обложек — тот же state, но превью отдаём как `file://` (или data-URL). Это рабочий план; я его НЕ рекомендую как основной по доводам выше, но он валиден, если приоритет — переиспользовать готовую вёрстку и минимизировать Swift-код.

## 3. Поток данных (конкретные механизмы)

### 3.1 Статус агента (вкл/выкл)
Источник истины — launchd. `EngineClient.agentStatus()`:
```
launchctl print gui/$UID/com.arrivarus.fb2toepub.agent
```
- Команда **успешна** (exit 0) и в выводе `state = running`/присутствует pid → агент загружен/активен.
- Команда **падает** (агент не загружен) → «не установлен/выключен».
- Парсим строки `state =`, `pid =`, `last exit code =`. (Запуск через `Process`, разбор stdout строками — без хрупких регэкспов на весь дамп.)

Управление (только при явном действии пользователя, через installer — единый владелец launchd-логики):
- Установить/перенастроить на папку: `bash installer.sh "<выбранная папка>"` (внутри: bootout→bootstrap→enable→kickstart -k, идемпотентно).
- Открыть папку: `open "<WATCH_DIR>"`.
- (Опц., M2) Пауза/выкл агента — `launchctl bootout gui/$UID/<label>`; включить обратно — повторный `installer.sh`. В макете явной кнопки выкл нет → не делаем в v1.

### 3.2 Отслеживаемая папка и смена папки
- Текущую папку читаем **из plist** (источник истины, что реально слушает launchd):
  ```
  plutil -extract EnvironmentVariables.WATCH_DIR raw -o - ~/Library/LaunchAgents/com.arrivarus.fb2toepub.agent.plist
  ```
- Смена («Сменить…» на обоих экранах): нативный `NSOpenPanel` (выбор папки) → `bash installer.sh "<новый путь>"`. installer сам перенастроит WatchPaths/Env и перезапустит агент идемпотентно. UI после успеха перечитывает статус.
- Первый запуск: если агента нет → по умолчанию сразу ставим на `~/Desktop/fb2-to-epub` (как в D8) — приложение при первом старте, если `launchctl print` падает, **само** вызывает `installer.sh` без параметра (дефолт), показывает экран «Готово к работе». Ручной старт не требуется (соответствует макету «Отслеживание активно»).

### 3.3 Последние конвертации + счётчики — **структурированный state-файл (JSON)**
**Рекомендация: watcher пишет `state.json`, UI его читает. НЕ парсим лог.**

Почему не лог: лог человекочитаемый, формат нестабилен (его меняли — см. строки про cover), парсить его в UI хрупко и привязывает UI к строкам лога. SQLite — оверкилл для счётчиков и списка из ~20 строк (тянет зависимость в bash; sqlite3 в watcher — лишняя сложность). JSON: пишется из bash без зависимостей (через маленький python-хелпер, python3 уже гарантирован движком), читается Swift через `Codable` тривиально.

Путь: `~/Library/Application Support/fb2-to-epub/state.json`.
Формат:
```json
{
  "schema": 1,
  "calibre_version": "7.21",
  "watch_dir": "/Users/<u>/Desktop/fb2-to-epub",
  "agent_label": "com.arrivarus.fb2toepub.agent",
  "totals": { "all": 1234, "today": 18, "today_date": "2026-06-25" },
  "recent": [
    { "src": "роман.fb2", "dst": "роман.epub", "ts": "2026-06-25T12:04:00Z", "cover": "online" }
  ],
  "cover_queue_count": 3,
  "updated_at": "2026-06-25T12:04:10Z"
}
```
Запись из watcher: **атомарно** (во временный файл рядом → `mv -f`), чтобы UI не прочитал полузаписанный JSON. `recent` — кольцевой буфер последних N (напр. 20). `today`/`today_date`: при первой конвертации нового дня today обнуляется. `all` — инкремент.
Чтение из UI: `StateStore` читает при старте + по событию `DispatchSource` (наблюдение за файлом) + лёгкий поллинг fallback (раз в ~2–3 c, пока окно открыто) на случай пропущенного события.

> Инвариант сохранён: «поведение конвертации не меняется». Запись state — это побочный лог-эффект рядом с уже существующим `log()`, не трогающий логику выбора что/как конвертить.

### 3.4 Проверка Calibre
- `EngineClient.calibreVersion()`: `/Applications/calibre.app/Contents/MacOS/ebook-convert --version` → распарсить версию. Нет файла → «не найден», экран Setup показывает шаг с инструкцией (как в макете, но в нативном виде; кнопка «Установить» открывает `https://calibre-ebook.com/download_osx`).
- Версию также дублируем в `state.json` (watcher знает её), чтобы статус-экран не дёргал процесс на каждый показ.

## 4. Механика очереди обложек (новая фича) — детально

### 4.1 Изменение cover-finder: режим top-N
Сейчас скрипт качает кандидатов по очереди и печатает ПЕРВЫЙ подходящий (exit 0). Расширяем **без слома текущего контракта**:

- Добавить режим (флаг `--emit-candidates <out_dir>` или 2-й режим запуска): вместо «скачать один в dst» — **отобрать до N (напр. 5) валидных кандидатов**, скачать их превью в `out_dir`, и вернуть машиночитаемый JSON в stdout:
  ```json
  {
    "title": "Война и мир", "author": "Лев Толстой",
    "best_index": 0,
    "candidates": [
      { "host": "Open Library", "url": "https://covers.openlibrary.org/b/id/123-L.jpg",
        "preview": "cand-0.jpg", "w": 600, "h": 900, "auto_best": true },
      { "host": "labirint.ru", "url": "…", "preview": "cand-1.jpg", "w": 480, "h": 720 }
    ]
  }
  ```
- `best_index` = текущая логика «первый прошедший фильтр» (соотношение 1.0–2.5, ширина ≥200). Менять критерий «лучшего» не нужно — переиспользуем `looks_like_cover` + порядок источников.
- Дедуп по URL уже есть (`seen`); добавить лёгкий дедуп по размеру/первым байтам, чтобы не показывать визуальные дубли (best-effort).
- Старый режим (1 аргумент-источник + dst, exit 0/1/3) **остаётся** — watcher для случая «0/1 кандидат» зовёт его как сейчас.

### 4.2 Решение в watcher: когда заводить очередь
В `convert_book` после `has_embedded_cover`-проверки:
- встроенная есть (rc=3) → как сейчас;
- иначе зовём cover-finder в режиме top-N:
  - **0 кандидатов** → конверт без обложки (как сейчас, `--no-default-epub-cover`);
  - **1 кандидат** → ставим её сразу (как сейчас), очередь не трогаем;
  - **2+ кандидатов** → ставим `best_index` сразу (НЕ блокируя), epub готов с лучшей обложкой; **затем** создаём запись очереди «ожидает выбора» с превью всех кандидатов; инкремент `cover_queue_count` в state.
- Это ровно решение человека: лучшую — сразу, остальное — в очередь, без поп-апов.

### 4.3 Файловая очередь — где и формат
Каталог: `~/Library/Application Support/fb2-to-epub/cover-queue/`
Одна книга = один подкаталог (имя = стабильный id, напр. sha1 от пути epub):
```
cover-queue/
  <id>/
    item.json
    cand-0.jpg  cand-1.jpg  cand-2.jpg   # скачанные превью
    applied.json        # появляется ПОСЛЕ применения (маркер «обработано»)
```
`item.json`:
```json
{
  "schema": 1,
  "id": "<sha1>",
  "epub_path": "/Users/<u>/Desktop/fb2-to-epub/война-и-мир.epub",
  "src_name": "война-и-мир.fb2",
  "title": "Война и мир", "author": "Лев Толстой",
  "best_index": 0,
  "applied_index": 0,            // что реально стоит в epub сейчас (изначально = best)
  "candidates": [ {…как из cover-finder…} ],
  "created_at": "2026-06-25T12:04:00Z",
  "status": "pending"            // pending | resolved | skipped
}
```
**Очередь по одному файлу на книгу** (а не один общий queue.json) — нет гонок записи между watcher (добавляет) и приложением (помечает решённым): они пишут разные файлы. Это устойчивее к параллельным конвертациям.

### 4.4 Как UI читает очередь и пишет выбор
- `CoverQueue.list()` — перечислить подкаталоги со `status=pending` (где нет `applied.json` или `status≠resolved/skipped`), отсортировать по `created_at`. Счётчик в шапке статус-экрана и бейдж «Выбрать обложку N».
- Экран «Выбор обложки» рисует одну книгу за раз (как в макете: «1 / 3»), превью — из локальных `cand-*.jpg` (`NSImage(contentsOfFile:)`), выбранный = `applied_index` (по умолчанию подсвечен авто-выбор `best_index`).
- Действия:
  - **Применить обложку** (выбран другой кандидат) → UI пишет «запрос на применение»: создаёт `request.json` в каталоге книги (`{"action":"apply","index":2}`) — применение делает движок-сторона (см. 4.5), ИЛИ приложение зовёт `cover-apply` напрямую (проще, см. ниже). После успеха — `status=resolved`, переход к следующей.
  - **Оставить авто-выбор** → `status=resolved` (epub уже с best, ничего не переобрабатываем) → следующая.
  - **Пропустить** → `status=skipped` → следующая (можно вернуть позже; в v1 — просто убираем из активной очереди).
- После любого действия пункт уходит из очереди, счётчики в state обновляются.

### 4.5 Применение выбора (переобработка epub) и кто его делает
Применять обложку к **готовому** epub нужно БЕЗ полной переконвертации:
```
/Applications/calibre.app/Contents/MacOS/ebook-polish --cover "<preview-или-полноразмер>.jpg" "<epub>" "<epub>"
```
(`ebook-polish` правит epub на месте, быстро; `ebook-meta "<epub>" --cover=<img>` — альтернатива, тоже без переконвертации). Для «полноразмерной» картинки лучше дозакачать оригинал по `url` выбранного кандидата (превью может быть мелким) — это делает та сторона, что применяет.

**Кто применяет — два варианта (выбор человека/Юрки):**
- **Вариант A (рекомендую): применяет приложение напрямую.** UI зовёт маленький скрипт `cover-apply` (`ebook-polish`) через `Process`. Плюсы: мгновенный отклик в окне, проще трассировать ошибку, не зависим от того, проснётся ли агент. Минус: запись в epub идёт из приложения — но epub лежит в watch-папке; **если папка под FDA-защитой (Desktop), приложению тоже может понадобиться доступ.** Это и есть ключевой нюанс (см. Риски R1).
- **Вариант B: применяет агент (runner уже имеет FDA).** UI кладёт `request.json`; watcher при следующем пробуждении (или мы «пинаем» его `launchctl kickstart`) видит запрос и применяет через свой FDA-доступ. Плюс: переиспользуем уже выданный FDA runner-а, приложению доступ не нужен. Минус: асинхронность (задержка/пробуждение), сложнее показать ошибку в реальном времени.

Моя рекомендация: **A с фолбэком на B** — пробуем применить из приложения; если запись запрещена TCC → кладём `request.json` и kickstart-им агент (у него доступ есть). Финальный выбор — за человеком на гейте, т.к. это про UX отклика vs. лишний FDA-промпт.

### 4.6 IPC агент ↔ приложение
Только через файлы + наблюдение каталогов (никаких сокетов/демонов у приложения):
- Приложение → следит `DispatchSource.makeFileSystemObjectSource` за `cover-queue/` (новые книги) и за `state.json` (метрики). Пока окно открыто.
- Приложение → агент: `request.json` в каталоге книги (если выбран Вариант B) + опц. `launchctl kickstart -k gui/$UID/<label>` чтобы не ждать.
- Агент → приложение: пишет `item.json`/превью/`state.json`; приложение реагирует на события.
- `DispatchSource` иногда пропускает события при пакетных изменениях → добавляем лёгкий **debounce + поллинг каждые ~2–3 c**, пока окно активно (дёшево, надёжно).

## 5. Изменения в движке (сводка, всё аддитивно)
1. **cover-finder.py**: новый режим top-N (флаг), вывод JSON-кандидатов + скачивание превью в каталог; старый режим сохранён. Критерий «лучшего» не меняем.
2. **watcher.sh**: после конвертации — ветка «2+ кандидатов → завести запись очереди + поставить best»; запись `state.json` (атомарно, кольцевой `recent`, счётчики). Поведение «что/как конвертить» НЕ меняется.
3. **cover-apply** (новый скрипт): применить обложку к готовому epub через `ebook-polish --cover` (или `ebook-meta --cover`); дозакачать полноразмер по url при необходимости. Зовётся приложением (A) или watcher-ом по request.json (B).
4. **installer.sh / plist**: добавить env-пути каталогов state/очереди (если фиксируем их вне дефолта App Support); FDA-логика без изменений. runner.sh — **не трогать**.
5. Каталоги: `~/Library/Application Support/fb2-to-epub/{state.json, cover-queue/}` — создаются installer-ом и/или watcher-ом при первом запуске.

## 6. Сборка / подпись / упаковка

### Сборка нативного приложения без .xcodeproj
- Структура SwiftUI-приложения как **SPM-пакет** (`Package.swift`, executable target) → `swift build -c release` даёт бинарь.
- `.app`-бандл собираем **скриптом** (расширяем существующий `build/build-app.sh` или новый `build/build-native-app.sh`): создать `Contents/{MacOS,Resources}`, положить бинарь в `MacOS/`, написать `Info.plist` теми же `plutil`-командами (тот же `CFBundleIdentifier=com.arrivarus.fb2toepub`, версия, `LSMinimumSystemVersion=11.0`, `NSHighResolutionCapable`), положить `AppIcon.icns` (тот же пайплайн svg→cairosvg→sips→iconutil), **и положить в Resources те же** `installer.sh`, `runner.sh`, `watcher.sh`, `cover-finder.py`, `cover-apply`.
- Полный Xcode/`xcodebuild` НЕ обязателен для сборки бандла; toolchain (swift) уже стоит. (Если позже понадобится `.xcodeproj` — это апгрейд, не блокер v1.)

### Подпись (та же гонка FinderInfo в iCloud)
- **Переиспользуем существующий ретрай-блок** из `build-app.sh` 1:1: цикл до 5 попыток `find ._* -delete` → `xattr -cr` → `xattr -d com.apple.FinderInfo` → `codesign --force --deep -s -` → снова снять FinderInfo → `codesign --verify --deep --strict`. Это уже отлажено и закрывает iCloud-гонку. Нативный бинарь подписывается так же, как бандл апплета.
- Ad-hoc (`-s -`), без платной подписи (D2). Gatekeeper-обход при первом запуске — как сейчас (ПКМ→Открыть / снятие quarantine).

### DMG — переиспользуем как есть
- `build/make-dmg.sh` + `dmg-settings.py` (dmgbuild) работают с любым `.app` в `build/dist/` — **менять не нужно**: та же геометрия 920×440, тот же фон, тот же drop-link `/Applications`, тот же volume-icon из `.icns`. Меняется только содержимое `.app`, не упаковка.

### Управление launchd-агентом из приложения
- Приложение НЕ дублирует launchd-логику: на установку/смену папки зовёт **bundled `installer.sh`** через `Process` (`/bin/bash <Resources>/installer.sh "<path>"`), читает его stdout/exit. Это ровно то, что делал AppleScript-апплет (`do shell script`), только из Swift. Идемпотентность и FDA-подсказки остаются внутри installer.

### Размер бандла
Нативный Swift-бинарь + Resources (скрипты + icns) — единицы МБ. Без веб-рантаймов и без бандла Calibre (D3). Меньше, чем webview-вариант не будет, но и не больше существенно.

## 7. Риски / неизвестные

- **R1 (главный) — FDA для применения обложки из приложения.** Если epub в Desktop/Documents/Downloads и обложку применяет приложение (Вариант A), запись в файл может упереться в TCC. Митигация: фолбэк на Вариант B (агент с уже выданным FDA применяет по request.json + kickstart). **Нужно решение человека + живой тест на этой машине** (как уже делали для runner-а). Это та же зона граблей, что в decisions/log.md (TCC на чистом профиле) → проверять вживую, не угадывать.
- **R2 — SwiftUI на macOS 11.** Часть API (Material/`.task`/некоторые модификаторы) — с 12. Митигация: таргет 11 + `if #available`; запасной ход — поднять флор до 12 (решение человека). Влияет на пиксель-перфект вибранси-фона (в макете фон — radial-gradient, его можно нарисовать вручную, не завися от `Material`).
- **R3 — пиксель-перфект тёмной темы.** Градиентная рамка выбранного кандидата (mask-composite в CSS), корешок-блик, тени, tabular-nums — на SwiftUI рисуются через `overlay`/`AngularGradient`/`mask`/`monospacedDigit`. Решаемо, но требует жёсткого design-review (гейт «≥1 несовпадение = FAIL»). Дизайн-спека (G3) обязательна до старта.
- **R4 — модель использования меняется (D1).** D1 говорил «одноразовый установщик, закрылся». Очередь обложек требует, чтобы окно **открывали повторно** (посмотреть статус, разобрать очередь). Это не противоречит D1 по сути (резидента/меню-бара по-прежнему нет), но приложение становится «открыл по необходимости», а не «один раз и забыл». Уведомлений о новых обложках в v1 нет (только бейдж при открытии) — подтвердить, что это ок (в макете так и есть: «показ — только очередь в окне»).
- **R5 — запись state.json из bash без зависимостей.** Генерация JSON в bash вручную = риск экранирования (юникод-названия книг). Митигация: писать через `python3` (уже гарантирован движком) — маленький инлайн-хелпер `json.dump`, не руками. Атомарность через temp+`mv`.
- **R6 — cover-finder скачивает превью N штук.** Больше сети/времени на книгу с 2+ кандидатами. Митигация: превью грузим маленькие (как есть, лимиты MIN/MAX_BYTES), top-N=5 максимум, таймауты уже стоят (8 c). Полноразмер качаем только при «Применить».
- **R7 — иконка статуса агента (вкл/выкл).** `launchctl print` формат вывода может отличаться между версиями macOS. Митигация: ориентироваться на exit-code (загружен ли) как primary-сигнал, парсинг `state =`/`pid =` как secondary; не падать на неожиданном формате.

## 8. Майлстоуны (validation-first, по зависимостям)

> Принцип: сначала доказать стыковку с движком на «скелете», потом наращивать UI. Каждый шаг — скриншот/проверка.

**M0 — Спайк стыковки (валидация рисков до вёрстки).**
Мини-SwiftUI-окно: вызвать `launchctl print` и показать статус агента; прочитать руками положенный тестовый `state.json` и отрисовать одну цифру; вызвать `installer.sh` на тестовой папке. **Done:** нативное окно реально читает статус движка и перенастраивает папку. (Снимает R7, доказывает «нативка стыкуется без моста».)

**M1 — Экран Статус на реальных данных.**
watcher пишет `state.json` (расширить watcher + python-хелпер). UI рисует hero/стат-карты/последние конвертации/папку из state. `DispatchSource`+поллинг. **Done:** кинул .fb2 в папку → окно через ~сек показало новую конвертацию и счётчики.

**M2 — Экран Установка/Готово.**
Calibre-чек, поле папки (из plist), «Сменить…» (NSOpenPanel→installer), FDA-подсказка, первый запуск ставит дефолт сам. **Done:** на «чистом» состоянии приложение проводит установку и показывает «Отслеживание активно».

**M3 — Движок очереди обложек (бэкенд).**
cover-finder top-N + watcher-ветка «2+ → очередь + best» + формат `cover-queue/<id>/`. **Done (гейт):** книга с 2+ найденными обложками → epub готов с лучшей + появилась запись очереди с превью.

**M4 — Экран Выбор обложки + применение.**
CoverSelectScreen по макету; превью из локальных файлов; действия Применить/Авто/Пропустить; `cover-apply` (`ebook-polish`) Вариант A с фолбэком B. **Done (гейт + живой FDA-тест R1):** выбрал другую обложку → она реально встала в epub; «Пропустить»/«Авто» корректно очищают очередь.

**M5 — Сборка/подпись/DMG нативного приложения.**
`build-native-app.sh` (SPM→бандл, тот же Info.plist/icns/Resources, тот же codesign-ретрай); DMG без изменений. **Done:** двойной клик по .app из DMG (после Open Anyway) проводит весь путь; `codesign --verify --deep --strict` ок.

**M6 — Пиксель-перфект + регрессия.**
Design-review всех 3 экранов side-by-side с макетом (лимит 3 цикла); QA desktop, 0 ошибок; проверка что движок-инвариант не нарушен (конвертация работает как раньше). **Done:** дизайн совпал поэлементно; релиз-кандидат.
